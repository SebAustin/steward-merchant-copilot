These resolve the cross-document contradictions plan-critic found in round 1 (67/100). Where a companion doc owns a topic, PLAN.md references it rather than restating it.

| # | Topic | Ruling | Owner doc |
|---|---|---|---|
| R1 | Doc ownership | AI-QUALITY.md owns models, routing, prompts, Untrusted Text format, evidence-ref grammar, eval commands, budgets and CI eval policy. | R2 | Failed executions (D7) | `failed` splits into `failed_retryable` (PayPal 5xx, timeout before any response, 429) and `failed_final` (4xx business errors). A retry from `failed_retryable` goes back to `executing` with the **same** `PayPal-Request-Id`. An unknown outcome is resolved by reconcile-by-read (GET the target in PayPal and decide executed or not). The DESIGN "Try again (safe, same request key)" copy stands. | PLAN + DESIGN |
| R3 | Approve atomicity (D1) | Approve and claim happen in one conditional UPDATE `proposed → executing` plus the approval insert, in one transaction. There is no standalone `approved` resting state for agent proposals. | PLAN |

| R5 | Model amounts (D10) | The model never authors money. Refunds carry `basis: full \| items \| shipping_only` plus `line_item_refs[]`, and code computes the amount. The Merchant may edit the amount at Approval; the edit is recorded in `edited_fields` and capped at the refundable remainder. | PLAN + AI-QUALITY |
| R6 | Standing Policy (D9) | NG4 is amended (REQUIREMENTS) to allow invoice-reminder policies only. Policy reminders use a deterministic template with **no model call** and no Untrusted Text. They run lazily when the queue or Brief loads and from a `/api/policies/run` route invoked by an external free cron (GitHub Actions schedule calling it with a secret header). There is no separate Render cron service. If the open-work index is hit, the policy skips that Invoice and counts the skip. Needs security-auditor sign-off at 0.5c. | PLAN + AI-QUALITY |
| R7 | Pipelines (D5) | The dispute desk, invoice chaser, risk explanations and Brief lines are pipelines (one structured-output call, no tools), triggered by explicit routes: `POST /api/disputes/:id/assess`, `POST /api/invoices/chase`, `POST /api/risk/explain`. | R8 | Brief LCP (D19) | Brief renders a deterministic template from DB-cached data first (counts, amounts, deadlines). Model-written lines stream in afterwards. | PLAN + DESIGN |

# Round 3 rulings (from plan-critic round 2, 77/100)

| # | Topic | Ruling | Owner doc |
|---|---|---|---|
| R16 | `subject_ref` (N1) | `subject_ref` = **capture ID** for `dispute_contest`, `dispute_accept` and `refund` (a SIM Dispute uses its linked seeded Order's capture). For `invoice_reminder` it is the Invoice ID. The derivation table goes in PLAN §5. This supersedes R4's wording. | PLAN |
| R17 | Unknown outcomes (N2, N3) | New state **`outcome_unknown`**. It stays in the open-work index, so the subject stays locked. It exits only via a confirmed read-back, a webhook, or an explicit Merchant "I checked PayPal: it happened / it didn't" action (audited). Failure classification: `failed_retryable` = **known not processed** only (connection refused, 429/5xx with a body proving no processing); anything after the request was sent without a definitive response → `outcome_unknown`. The retry route always runs `readBack` first when the last outcome was unknown or `requestIdReplaySafe=false`. Test: a replay-unsafe kind, post-send timeout, Merchant retry → exactly 1 write. I10 is reworded to "at most one write in flight per subject". | PLAN + DESIGN |
| R18 | Write modules (N4) | Three write modules, each enforced by the module-graph test: `writes.ts` (Merchant-facing; executor only), `topup-orders.ts` (create + capture card Orders; `features/demo` + `scripts`), `seed-writes.ts` (invoices, send, record-payment, tracking, refunds, dispute simulators, probe writes; `scripts/**` only). REQUIREMENTS NFR-S1 and SC-1 are amended accordingly (done). | PLAN |
| R19 | Shared Reset (N5) | Reset has a global cooldown (1 per 15 min), at most 12 per day, and at most 5 top-up Orders per reset. Confirm copy: "This resets the demo for everyone viewing it." The hosted smoke uses a cron-secret-only `POST /api/demo/topup` that creates one capture **without** bumping the epoch, and SIM Disputes. No per-session epochs (YAGNI). | PLAN + DESIGN |
| R20 | Eval spend (N6) | Nightly = `golden` suite only, and only when AI paths changed (~$3). The full suite runs only at tag gates (v0.3, v0.4, v0.5) plus one manual pre-submission run. A cumulative eval-spend guard sums `ai_runs` where `purpose='eval'` and refuses above **$90**. The project total stays ≤ $150 (A-9). | PLAN + AI-QUALITY |
| R21 | Probes (N7) | File **3** probe Disputes on Oct 6: one observe-only (P0-7), one for provide-evidence, one for accept-claim. Split P0-3 into **P0-3a** (remind + refund replay; 0.1b) and **P0-3b** (dispute writes; start of 0.3c). `requestIdReplaySafe=false` is the default until probed. The live grid moves out of 0.1b. | PLAN |
| R22 | Spend lock (N8) | The row lock is held only inside short reserve/settle transactions, never across a model call. Today's row is upserted before `FOR UPDATE`. Fixed lock order: `spend_days` then `sessions`. Unsettled reservations are released on abort or after a 10-minute TTL. Evals use their own budget scope. Reserve in `prepareStep`, settle in `onStepFinish`. | PLAN |
| R23 | Lazy work (N9) | No side effects on the render path. Lazy policy, reconcile and expiry run in Next `after()` under `pg_try_advisory_lock`. A DB CHECK enforces that a policy actor can approve only `invoice_reminder` Proposals it created (`created_by='policy'`). `/api/policies/run` documents its two auth modes: session + CSRF, or the cron secret header. | PLAN |
| R24 | Trapped retries (N10) | `failed_retryable` → `rejected` (Merchant abandons) and → `expired` (`expires_at` or reset). Reset transitions are drawn in the diagram. | PLAN + DESIGN |
| R25 | Housekeeping (N11–N14) | Correct the session count and state the v0.3 buffer. Schedule the AG Grid Community-fallback scope in 0.3c/0.4a, conditional on the Oct 20 decision.
